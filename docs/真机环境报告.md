## 4. 权限

| 项 | 状态 |
|---|---|
| 登录用户 | `orangepi`（uid=1000） |
| sudo | **免密可用**（`SUDO_NOPASSWD_OK`） |
| 所属组 | tty, disk, dialout, sudo, audio, video, plugdev, games, users, input, netdev, bluetooth, systemd-journal |
| **docker 组** | **不在组内** |

### sudo 免密的含义

部署与排障会省很大事。但**Agent 运行时仍按非 root 设计**（架构 §9），能力探测 + 降级脚本的逻辑不变。免密只意味着"生成的降级脚本执行起来更省事"，不代表 Agent 该主动提权。

### docker 组（已决策并执行）

`docker --version` 正常（29.6.1），但初始状态下 `orangepi` **不在 docker 组**，无法访问 `/var/run/docker.sock`。

**老板决策：加入 docker 组**（2026-08-29 17:15 执行完成）。

执行后验证（新会话，无 sudo）：

```
$ id orangepi
uid=1000(orangepi) gid=1000(orangepi) 组=1000(orangepi),5(tty),6(disk),20(dialout),27(sudo),
  29(audio),44(video),46(plugdev),60(games),100(users),999(systemd-journal),102(input),
  107(netdev),118(bluetooth),996(docker)

$ docker ps
wxedge    Up 2 hours

$ docker info --format '{{.ServerVersion}} | containers={{.Containers}} | running={{.ContainersRunning}}'
29.6.1 | containers=3 | running=1
```

`can_read_docker` / `can_write_docker` 探测结果均为 **true**。

**已认知的风险**：docker 组成员实际等同于 root（可通过挂载宿主机目录提权）。这是老板在知情前提下的明确选择。

**但 Agent 的降级逻辑一个字都不能少**：
- 这是单台节点的手工配置，不是 Agent 部署流程的一部分
- 将来纳管的新节点大概率没有加组，必须能走降级脚本路径
- 能力探测是**运行时**判定，不是编译期常量。同一份 Agent 二进制要在两种节点上都正确工作

### 业务容器（隔离红线）

`docker ps` 发现运行中的容器 **`wxedge`**（Up 2 hours），另有 2 个已停止容器。这是节点上的**真实业务**，也是负载偏高（load 8.11）的主要原因。

由此确立的硬约束（需求 A6 的具体化）：

- Agent 的容器写操作（stop / rm / restart）**默认作用域只限于 ECP 自己部署的容器**
- 用 label 标记归属，默认 `ecp.managed=true`；操作前校验 label，不匹配返回 `RESULT_STATUS_REJECTED`
- **禁止**任何"操作所有容器"的批量接口
- 只读操作（ps / logs / inspect）可查看全部，但列表须标注哪些是 ECP 纳管的、哪些不是

- 连接建立与关闭全部写审计日志
- **红线不变：只做网络可达，绝不绕过 1Panel 自身鉴权**，不读 `/opt/1panel` 下的凭据，不生成免密票据
