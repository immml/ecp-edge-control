## 关键决策

**1. proto 契约为核心，先定稿再并行开发。**
契约是所有模块的共同依赖，必须由我（主理人）先写死，后续工程师才能并行开工而不冲突。设计要点：
- `AgentService` 四个 rpc：`Register` / `CommandStream` / `Tunnel` / `UploadBacklog`
- 注册语义区分**首次绑定**与**重装自动重认证**（`RegisterReason`），直接承载用户的"上线即控"诉求——重装后无需人工审批，但每次都留痕
- `CapabilityReport` 能力探测上报，支撑"Agent 非 root"前提下的功能分级与降级
- 终端、文件传输、端口转发三种业务**复用同一条 `Tunnel` 流**，上层用 session_type 区分。它们底层都是双向字节流，统一后省掉三套连接管理逻辑
- `UploadBacklog` 承载控制面离线期间的数据补传，这是"控制面按需上线"架构的必需品

**2. Go 工具链装到 `D:/ecp-toolchain`，不装在项目 `.venv` 下。**
原因：项目路径含中文「边缘计算-算力节点」，Go 的 `asm.exe` 汇编器在交叉编译 **linux/amd64** 的 crypto 包时崩溃。**arm64 不受影响**，所以最初 arm64 编译成功一度让人以为环境没问题，直到编 amd64 才暴露。工具链路径必须无中文。
组件依赖缓存仍按用户规范隔离在 `.venv/<组件>/pkg/mod`，未破坏"虚拟环境隔离"的要求。

**3. proto 代码生成走本地插件，不走 buf.build 远程插件。**
国内访问 buf.build 不稳定。已本地安装 `protoc-gen-go` / `protoc-gen-go-grpc` / `buf` 到 `.venv/toolchain/bin`，`buf.gen.yaml` 配 `local:` 插件，生成过程零外部网络依赖。

**4. proto 独立成 module，server/agent 用 `replace` 引用本地路径。**
避免引入私有 module 代理即可跨模块共享契约，同时保证三份代码版本永远一致。

**5. 生成代码 `proto/gen` 入库。**
用户没有 CI 环境，生成代码不入库会导致合作者（和用户自己）无法直接 build。

## 遗留问题

1. **交叉编译必须绕过沙箱**。沙箱会杀掉 Go 汇编器进程，表现为命令零输出、直接 exit 1，极易误判。已记入 `开发日志/README.md` 的"环境已知问题"。
2. **控制机没有 Docker**，原架构依赖的 PostgreSQL / Redis / Mosquitto 三大件跑不起来。已作为 Q2 抛给架构师重新裁定（我倾向自包含 SQLite + 内存态，心跳遥测改走 gRPC 流从而砍掉 Mosquitto）。
3. **用户已指令砍掉 Cloudflare Worker**，改 Tailscale + P2P + FRP。架构 v2 设计中，原 `worker/` 目录的处置待架构师决定。
